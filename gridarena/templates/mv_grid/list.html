Power Flow Data Generation

Generates large amounts of realistic power-flow training data for one or more MV grids, by injecting power/voltage curves from a Historical database at each grid's connection points and solving the resulting power flow — including stressed, out-of-normal-limits states — without needing an optimizer to invent a synthetic dispatch. Only the MV grid itself is ever solved: no LV-level power flow is run, so the output is strictly the MV topology's P/V values and branch flows.

Each generated scenario is one timestamp from the chosen database's own shared timeline. Optionally, that base scenario is then re-solved against one or more perturbed variants of the grid, described below.

  • Data Source — MV: if the chosen database's series are tagged MV, every connection point in the grid gets its own randomly-drawn series as its injection directly — no real LV grid needs to be connected anywhere.
  • Data Source — LV: if tagged LV, only connection points that already have a real LV grid attached are populated; for each one, as many LV series as that LV grid has nodes are randomly drawn and summed to form the injection — synthetic per-node curves standing in for real per-node measurements.
  • Data Source — Feeder: if tagged Feeder, the same connection points as LV mode are used; the number of connected points determines how many feeder series are drawn (one per point, distinct where possible) and used directly as that point's injection.
  • Total Timesteps / Reassignment Period: Total Timesteps picks how many timestamps from the database's shared timeline to use as scenarios. Reassignment Period then groups those scenarios, in timestamp order, into blocks of that many — every block gets its own random series-to-point assignment, so e.g. a Total Timesteps of 1000 with a Reassignment Period of 100 produces 10 different random assignments across the run, not one fixed mapping throughout. A database mixing more than one grid_level among its series can't be used; upload homogeneous databases per source type.
  • Topology Perturbation — None: solve every scenario once, against the grid's real, unmodified topology only.
  • Topology Perturbation — Exhaustive N-k: systematically enumerates every possible combination of up to k branches being simultaneously taken out of service (every single-branch outage, then every pair, and so on up to k) and solves each scenario against every one of those variants — a complete contingency sweep. Because these grids are radial (tree-shaped), disabling a branch always islands everything downstream of it; that islanded subtree is simply excluded from that variant's results rather than discarding the whole variant. The number of variants grows combinatorially with k, so a very large k on a big grid may be rejected as infeasible — use Random instead in that case.
  • Topology Perturbation — Random: instead of enumerating every combination, randomly samples a chosen number of outage combinations (1 to k branches at a time). Useful when a grid has too many branches for exhaustive enumeration to be practical.
  • Admittance Perturbation: independently redraws every branch's resistance and reactance within ±sigma of its real, original value — modelling parameter uncertainty (aging equipment, imprecise cable/line specs), layered on top of whichever topology variant is being solved.
  • Load Noise (sigma): optional per-bus multiplicative noise added on top of whichever value was assigned, for extra scenario diversity beyond the source data alone.
